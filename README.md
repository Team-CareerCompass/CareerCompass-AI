# CareerCompass-AI

건국대학교 졸업 프로젝트 **CareerCompass** 의 AI/NLP 서비스.

공고 본문을 구조화하고, 사용자 프로필과 대조해 적합도를 산출하고, 경험 카드를 근거로 자기소개서 초안을 만드는 부분이 여기 있다.

담당은 **서성덕 (@kislevite)** — 2026-05-18 제안서 「팀원 정보」의 역할이 AI/NLP 다.

> 2026-03-06 제안서(`… – CamBridge`)는 **폐기된 주제의 문서**다. 거기 적힌 역할 분담은 현행이 아니다.

**정본은 [`docs/AI_CONTRACT_v0.1.md`](docs/AI_CONTRACT_v0.1.md) 다.** BE 가 무엇을 보내고 무엇을 받는지, 그리고 왜 그렇게 정했는지가 거기 있다.

## 현재 상태

**골격까지 섰다.** 계약대로의 엔드포인트 6개가 **더미 응답**을 낸다. 모델은 아직 부르지 않는다.

| 마일스톤 | 범위 | 상태 |
| --- | --- | --- |
| **A0 기반** | 골격·게이트웨이·프롬프트 관리·스키마 검증·평가셋·PII 경계 | #1 완료 · #6 초안(계약 D4) · 나머지 진행 전 |
| **A1 공고 파싱** | 구조화 파싱·마감일·처리 상태·양식 인식 | 계약 확정 · 구현 전 |
| **A2 적합도** | 4축 산출·경쟁 강도·산출 불가·코멘트·유사 공고 | 계약 확정 · 구현 전 |
| **A3 지원서 생성** | 항목별 초안·카드 우선순위·톤·재생성·스트리밍 | 계약 확정 · 구현 전 |
| **A4 문서 분류** | 텍스트 추출·항목 분류 6종·신뢰도 | 계약 확정 · 구현 전 |
| **A5 추천·로드맵** | For You·코호트 비교·강점 요약 | 계약 미작성 |
| **A6 운영·품질** | 캐싱·비용 측정·가드·계약 대조 CI·배포 | 진행 전 |

이슈 **31건**, 마일스톤 7개(A0~A6).

### 다음에 할 것

1. **#6 PII 문서** — 계약 D4 가 초안이다. 기능별로 실제 보내는 필드를 확정해 BE #48 과 맞춘다.
2. **#2 게이트웨이** — `CC_STUB_MODE=false` 일 때 실제 프로바이더를 부르는 층. **응답 리플레이 캐시를 여기서 같이 넣는다** — 그래야 개발 중 LLM 비용이 0 에 수렴한다.
3. **#7 공고 파싱** — 파싱 결과가 적합도와 지원서 생성의 입력이라, 여기가 서면 A2·A3·A4 가 병렬로 갈라진다. 착수 전에 `fixtures/postings/` 를 채운다.

## 띄우기

```bash
python -m venv .venv && .venv/bin/pip install -e ".[dev]"   # Windows: .venv\Scripts\pip
uvicorn app.main:app --reload
curl localhost:8000/health
```

또는 `docker compose up --build`.

호출에는 `X-Internal-Token` 헤더가 필요하다(`/health` 는 예외). 기본값은 `.env.example` 참고.

```bash
curl -X POST localhost:8000/v1/parse-posting \
  -H 'Content-Type: application/json' -H 'X-Internal-Token: dev-token' \
  -d '{"postingId":101,"title":"테스트","rawContent":"..."}'
```

### 더미 응답을 고르는 법

고정 응답만 내려주면 BE 가 실패 화면을 짤 수 없다. `postingId` 로 시나리오를 고른다.

| postingId | 결과 |
| --- | --- |
| 999001 | `status: partial` — 마감일·양식 없음 |
| 999002 | `PARSING_FAILED` / `NO_KEYWORDS` |
| 999003 | `PARSING_FAILED` / `IMAGE_ONLY` |
| 999004 | `PARSING_FAILED` / `NOT_A_POSTING` |
| 999005 | `PARSING_FAILED` / `EMPTY` |
| 그 밖 | `status: ok` |

타임아웃 처리를 시험하려면 `?delay=15000` (밀리초).

## 정해진 것

근거는 계약 §0 에 있다.

- **이 서비스는 상태를 갖지 않는다.** 큐·재시도·작업 상태·FE 로 나가는 SSE 는 전부 BE 가 한다. 양쪽에 큐를 두면 장애 시 진실이 두 개가 된다.
- **임베딩 저장·검색은 BE 소유다.** MVP 에서는 그것조차 미루고, BE 가 경험 카드를 요청에 실어 보낸다. 카드는 사용자당 최대 30개고, 30개에 ANN 인덱스는 과설계다.
- **PII 경계는 기능별로 다르다.** 공고는 공개 텍스트라 프로바이더가 자유고, 자소서·경험·프로필이 닿는 기능만 국내 처리로 묶는다.
- **자소서 항목 분류는 프롬프트 기반이다.** 명세서 F1-4 가 「llm api 혹은 오픈소스 BERT 파인튜닝」 두 갈래를 남겼으나, 보고서 4.4.2 가 「6개 항목이 의미적으로 잘 구분되므로 프롬프트 기반 방식으로 충분한 정확도를 얻는다」로 결론지었다. **KoBERT 파인튜닝은 기본안이 아니다.** 정확도가 안 나오면 그때 파인튜닝을 보되, 학습 데이터를 구할 수 있는지가 먼저다.
- **파이썬 서비스인 이유**는 파인튜닝 때문이 아니라 프롬프트·평가셋을 빠르게 돌려야 하기 때문이다(#5). BE 는 HTTP 로 부른다.

**프로바이더**는 서울 리전 인리전 온디맨드에 2024년 모델 두 종(Claude 3.5 Sonnet · Claude 3 Haiku)만 있다는 것을 확인했다. 인리전 추론 자체는 성립하므로 보고서 4.4.1 의 전제는 지켜진다. 다만 지원서 생성이 건당 132원 대 35원으로 갈려서, HCX 를 함께 검토 중이다. **#2 게이트웨이는 두 프로바이더를 모두 어댑터로 두고, 평가셋으로 비교한 뒤 고른다.**

## 규약

- 스펙과 다르게 구현하기로 정했으면 `docs/API_SPEC_v0.1.md`(BE 저장소)를 고치고 해당 저장소에 이슈로 알린다. 조용히 다르게 만들지 않는다.
- **계약과 `app/schemas.py` 는 함께 고친다.** 한쪽만 바꾸지 않는다.
- 프롬프트를 고치면 평가셋을 돌린다(#5). 눈으로 두세 개 보고 넘어가지 않는다.
