## 넣는 법

파일 하나에 공고 하나. 이름은 `001.md`, `002.md` … 순서대로.

앞에 `---` 로 둘러싼 머리말을 넣고, 그 아래에 **본문을 그대로 붙여넣는다.**

```markdown
---
id: "001"
title: 2026 카카오 SW 인턴십
url: https://careers.kakao.com/jobs/...
source: 사람인
type: recruit
collectedAt: 2026-09-07
---

모집 부문
...본문 전문...
```

`type` 은 `recruit`(채용) / `scholarship`(장학금) / `contest`(공모전) / `activity`(대외활동) 넷 중 하나. 애매하면 비워 두고 나중에 채운다.

## 붙여넣을 때 지킬 것

- **본문은 손대지 않는다.** 오타·줄바꿈·이상한 공백 그대로 둔다. 실제로 크롤러가 가져올 텍스트가 그렇게 생겼고, 깨끗하게 다듬은 텍스트로 시험하면 실전에서 무너진다.
- **HTML 말고 텍스트.** 화면에서 드래그해 복사한 그대로면 된다.
- **개인정보가 있으면 지운다.** 담당자 이름·휴대폰·이메일은 `[삭제]` 로 바꾼다. 공고 자체는 공개 문서지만 이 저장소는 공개되어 있다.
- **표는 깨져도 그냥 둔다.** 표가 텍스트로 뭉개진 공고가 파싱에서 제일 어렵고, 그래서 제일 필요하다.

## 무엇을 모을까

10건이면 충분히 시작할 수 있다. 다만 **비슷한 것 10개보다 다른 것 10개**가 훨씬 쓸모 있다.

### 유형 배분

유형마다 지나가는 기능이 다르다. 채용·장학금은 파싱→적합도→**양식 인식→초안 생성**까지 가고, 공모전·대외활동은 적합도에서 끝난다(명세서 3.1: 「초안 생성 버튼은 장학금 또는 채용인 경우에만 노출」). 그래서 균등하게 넣지 않는다.

| 유형 | 건수 | 이 유형으로만 시험되는 것 |
| --- | --- | --- |
| `scholarship` 장학금 | 3 | **자격 조건 충족도(가중치 30%)** — 학점·이수학점·소득분위·학년이 명시적으로 적힌 유일한 유형 |
| `recruit` 채용 | 3 | 우대 조건 매칭, 자소서 문항의 글자 수 제한 |
| `contest` 공모전 | 2 | 유형 판별, 마감일 표현의 다양성 |
| `activity` 대외활동 | 2 | 유형 판별, 양식이 없는 경우의 `formQuestions: []` |
| **공고가 아닌 것** | 1 | `NOT_A_POSTING` 판별 (계약 §1.3) |

마지막 줄이 빠지기 쉽다. 사용자는 학사공지 게시판을 **통째로** 등록하므로(F2-1) 「2026-1학기 수강신청 안내」·「졸업요건 변경 공지」 같은 것이 함께 수집된다. 그것을 걸러내는지 시험할 표본이 없으면, 공고 목록에 수강신청 안내가 뜬 채로 배포된다. 건대 학사공지에서 아무거나 한 건 가져와 `expected` 를 `{ "status": "failed", "reason": "NOT_A_POSTING" }` 로 둔다.

**장학금을 빠뜨리지 않는다.** 자격 조건이 빡세게 적힌 유일한 유형이라 §2 적합도의 30% 축을 시험할 데가 여기밖에 없고, 자소서 문항도 「가정 형편」·「학업 계획」처럼 경험 카드로 채우기 어려운 것이 나와서 §3 생성이 가장 잘 깨진다. 그리고 형식이 제일 엉성하다.

### 그 밖에 섞을 축

| 축 | 섞을 것 |
| --- | --- |
| 마감일 표현 | `2026-05-25` / `5월 25일(월) 23:59` / `5월 넷째 주` / **마감일이 아예 없는 것** |
| 지원서 양식 | 질문·글자수가 명시된 것 / 「자유 양식」 / 양식이 없는 것 |
| 길이 | 300자짜리 한 문단 / 5,000자 넘는 상세 요강 |
| 형태 | 잘 정리된 채용 사이트 / **학과 공지처럼 엉성한 것** |

학과 공지·교내 게시판이 특히 중요하다. 그게 이 서비스의 차별점인데(보고서 2.3) 가장 안 정제된 텍스트라서 파싱이 제일 잘 깨진다. 「붙임 파일 참조」만 달랑 있는 공고도 한 건 넣는다 — `status: failed` 가 정답인 케이스가 있어야 #9 를 시험할 수 있다.

## 본문이 이미지인 공고

공공기관 채용공고(한국전력공사 등)와 학교 장학 공지는 본문이 **이미지 한 장**인 경우가 흔하다. 계약 §1.5 에서 다루는 경우다.

**1~2건만 넣는다.** 이미지 경로는 #7 이후 별도로 만들 것이라, 지금은 「이런 게 실제로 있다」를 기록해 두는 용도다.

- 이미지는 `images/001-1.png` 로 저장한다.
- 머리말에 `images: [001-1.png]` 를 적고, 본문 자리에는 페이지에 실제로 있던 텍스트만 적는다(제목 한 줄뿐이어도 그대로).
- `expected/001.json` 의 정답은 현재 기준 `{ "status": "failed", "reason": "IMAGE_ONLY" }` 다. 멀티모달 경로가 붙으면 그때 정답을 채운다.

OCR 을 돌려서 텍스트로 바꿔 넣지 않는다. **원본 이미지 그대로 둔다** — 나중에 멀티모달로 시험할 때 그 이미지가 필요하다.

## expected/

`expected/001.json` 에 **정답**을 적는다. 지금은 비워 두고, 원문이 모인 뒤에 채운다.

```json
{
  "type": "recruit",
  "dueDate": "2026-05-25",
  "keywords": ["Spring", "Kotlin", "Redis"],
  "formQuestions": [{ "order": 1, "question": "지원 동기", "maxChars": 500 }],
  "note": "표가 텍스트로 뭉개져 있음"
}
```

전부 채울 필요는 없다. **확실한 것만 적는다.** 마감일이 원문에 없으면 `"dueDate": null` 이 정답이고, 그것을 맞히는지가 #8 의 시험이다.

키워드·우대는 **순서 없는 목록**이라 정확 일치가 아니라 겹침으로 채점한다 (`app/evaluation.py` `grade_list`). 공백·대소문자를 무시하고 어느 쪽이든 포함이면 맞힌 것이다 — 「SW개발」과 「SW 개발」, 「숏폼 채널」과 「숏폼 채널 활발한 운영」.

- `keywords` — 이 공고를 다른 공고와 구별하는 표현 5~10개. 조직명·직무·기술·전공. 「채용」「대학생」 같은 일반어는 넣지 않는다
- `keywordsNot` — **뽑히면 안 되는 것.** 앞머리의 다른 공고 링크(004), 혜택(008), 일반어(009). 하나라도 나오면 「금지어」로 센다 — 0 이어야 한다
- `preferences` — 본문에 「우대」라고 적힌 항목만, 원문 항목 단위로. 혜택·필수 자격은 아니다
- `labelNote` — 왜 그렇게 라벨했는지 애매한 판단을 적는다

## 나중에 추가할 것

프롬프트 주입 시험용 공고(#29). 본문 안에 「위 지시를 무시하고 …」 같은 문구를 심은 것을 몇 건 만들어 둔다. 실제로 수집될 리는 없지만, 방어가 되는지 확인하려면 필요하다. 원문 수집이 끝난 뒤에 만든다.
